How the Trading Table Works

A plain-English guide to the live Basket Orders table: what each file does, how scrolling through a huge list stays fast, and what happens when a price changes on the server.

Who this is for Anyone on the team, including people who don't write React every day. Technical words are explained the first time they appear and again in the glossary at the end.

0. Why the development build uses so much more CPU than production

Short answer npm run dev runs a version of React built for finding bugs. It deliberately renders everything twice, runs extra checks on every render, and records extra debugging information. npm run build + npm run preview runs the version built for speed, with all of that removed. It's the same app code, but a very different amount of work per update.

An analogy: the development build is a car on a test track with sensors on every part and an engineer writing notes after every lap. The production build is the same car with the sensors taken off. Both drive the same route, but one carries far more overhead.

What the development build does extra, on every update

Extra work in developmentWhat it means in plain termsCost for our live table
StrictMode double rendering
(<StrictMode> in main.tsx)		 React runs every component's render function twice and throws the second result away. This catches code that behaves differently when run twice. It only happens in development. Every flush (up to 4 per second) renders the table and every changed row twice, doubling the rendering work.
Development build of React React ships two versions of itself. The development version checks things as it goes: missing keys, wrong hook order, invalid props, and it tracks which component created which, so error messages can point at the right line. Every one of the thousands of cells rendered pays for these checks.
Performance-timeline logging React 19's development build writes timing entries for component renders so that they show up in Chrome's Performance panel. Extra bookkeeping on every render. It's useful for debugging, but it isn't free.
Unoptimized code The dev server serves code as-is: not minified, not bundled, and with development-only branches left in. Production removes every if (development) { … } block entirely. Slower page start-up, and more code runs on every update.
Dev tooling Vite's hot-reload connection, source maps, and (if installed) the React DevTools extension, which inspects every render. Small but constant background work, and more with DevTools open.

The same update. In development React does roughly double the rendering plus extra checks. In production it does one lean pass.

Why this matters so much for this app

Most web pages render once and then sit idle, so the development overhead is barely noticeable. A live trading table is the opposite: it re-renders up to 4 times a second, forever, across dozens of columns. Any per-render overhead gets multiplied by the number of renders, so a fixed extra cost per render becomes a constant CPU load in development.

What this means in practice

  • Judge performance only on the production build. Run npm run build, then npm run preview (port 4173). Close DevTools and read the tab's CPU in Chrome's Task Manager (Shift+Esc). Rebuild after every code change: the preview server doesn't hot-reload.
  • Use the development build for writing and debugging code, not for measuring speed. High CPU in npm run dev is expected and doesn't mean users will see it.
  • Don't remove <StrictMode> to "fix" development CPU. It has no effect in production, and it's what helped us find the WebSocket bug (section 13).
  • console.log costs CPU in both builds, especially with DevTools open. Remove debugging logs, such as a log inside the table's render, before measuring.
Result on this project After these changes, the production build (npm run preview) showed low CPU usage while the table was live. The development server still showed high CPU. That's the expected gap described above, not a problem in the table itself.

1. The big picture

The page shows a table of basket orders that come from an AMPS server (a real-time messaging database). There can be thousands of orders, and prices change many times a second.

Showing all of them at once would be like printing an entire phone book every time one phone number changes. So the app does three things instead:

  1. Only ask the server for the rows near what you're looking at. Roughly 50–70 rows at a time, not the whole list. This is the server window.
  2. Only draw the rows that fit on screen. Even of those ~70 rows, only the ~20–30 you can actually see (plus a few spare) are drawn. This is virtualization.
  3. Collect price changes and apply them in batches. At most 4 times a second, and only redraw the rows whose values actually changed. This is the flush.
An everyday analogy Think of a train window. The landscape (all the orders) is huge, but you only ever see what's in the window. The app is the train crew: it fetches the scenery just ahead of the window before you get there, and only repaints the bits of scenery that changed.

2. What was wrong before

The previous version worked, but it had several problems that made it slow and confusing:

ProblemWhat the user sawWhat we changed
The table was told the total row count, but the value was silently ignored (hidden behind an as any type cast). The scrollbar only covered ~51 rows. Scrolling near the bottom made the content jump, and you could never smoothly reach rows further down. The table now accepts rowCount and rowOffset properly, so the scrollbar represents the full server total.
Every scroll event redrew the whole table immediately (the virtualizer's default "flushSync" mode). Console warning: "'scroll' handler took Xms". Janky scrolling. Turned that off (useFlushSync: false) and made rows remember themselves (memoization).
Every update redrew every visible cell and the whole header. Console warning: "'message' handler took 468ms". High CPU. Rows and the header are now memoized: only changed rows redraw.
The flush copied the whole row list once per change, and redrew even when nothing had changed. Wasted CPU on every update. One copy per batch, and unchanged values are skipped.
Number formatting created a new formatter for every single cell. Slow rendering with ~25 numeric columns. One cached formatter per number of decimal places.
In development, React mounts components twice (StrictMode), and the first socket was closed while still connecting. Console warning: "WebSocket is closed before the connection is established". The connection starts one moment later, so only the surviving mount ever opens a socket.
Row heights were estimated at 50px, but rows were really about 45px. Scroll position drifted slightly. Every row is now exactly 45px.
The header's scroll wrapper was the wrong element. The header scrolled away, and the sideways scrollbar sat below every row, at the very bottom of the list. The table sits directly in the scroll box, so the header stays pinned and sideways scrolling works normally.
If you scrolled quickly, an older subscription could be left running. Extra hidden network traffic. Every subscription that's no longer needed is now always cancelled.

4. How virtualization works (TanStack Virtual)

Imagine a list of 10,000 rows, each 45 pixels tall. That's 450,000 pixels of content, but your screen only shows about 20 rows. Drawing all 10,000 rows would take a lot of memory and time.

Virtualization fakes it. The browser is given a scroll area of the full height, but only the rows you can see are real. Above and below them are two invisible "spacer" rows that take up the rest of the height, so the scrollbar looks and behaves exactly as if everything were there.

flowchart TB
  subgraph sb["Scroll box: what the browser thinks it has"]
    direction TB
    top["Top spacer row
empty, height = rows above x 45px
e.g. 4,000 rows x 45 = 180,000 px"]
    r1["Row 4,000 (drawn)"]
    r2["Row 4,001 (drawn)"]
    r3["... about 20-30 drawn rows ..."]
    r4["Row 4,030 (drawn)"]
    bottom["Bottom spacer row
empty, height = rows below x 45px"]
    top --> r1 --> r2 --> r3 --> r4 --> bottom
  end

Only the middle part is real. The spacers are empty cells with a fixed height.

The steps, every time you scroll

  1. The browser reports how far down you've scrolled, for example 180,000px.
  2. The virtualizer divides by the row height: 180,000 ÷ 45 = row 4,000 is at the top.
  3. It works out how many rows fit on screen, then adds 10 extra ("overscan") above and below so fast scrolling doesn't show blank gaps.
  4. It returns that list of row numbers. The table draws just those, plus the two spacers.
flowchart LR
  s["You scroll"] --> o["Browser: scrollTop = 180,000px"]
  o --> v["Virtualizer:
180,000 / 45 = row 4,000"]
  v --> r["Visible rows 4,000-4,020
+ 10 overscan each side"]
  r --> d["Table draws rows 3,990-4,030
plus top and bottom spacers"]
Why a fixed row height matters The simple division above only works if every row is the same height. That's why every row is now exactly 45px (rowHeight in DataTable). If rows were different heights, the virtualizer would have to measure each one, which costs time.

5. The server window (paging with AMPS)

Virtualization saves drawing. But we also don't want to download all 10,000 rows. So we ask AMPS for just a slice, using two options:

  • skip_n: how many rows to skip from the top.
  • top_n: how many rows to return.

For example, skip_n=3975, top_n=71 means "give me rows 3,975 to 4,045 in the current sort order". That's the visible rows plus 25 spare rows on each side (VIEWPORT_BUFFER).

The table is told three things:

SettingMeaningExample
rowCountHow many rows exist on the server. This sizes the scrollbar.10,000
rowOffsetWhich row number the loaded slice starts at.3,975
dataThe loaded rows themselves.71 rows

When the virtualizer asks for row number 4,000, the table looks up data[4000 - 3975], which is data[25]. If that position isn't loaded (for example, you just scrolled somewhere new), a grey skeleton row is shown until the data arrives.

8. Example: scrolling down

Say rows 0–50 are loaded and you scroll down so that rows 35–55 are on screen.

  1. The virtualizer tells the hook "rows 25–65 are drawn" (visible rows plus overscan).
  2. The hook waits 150ms (RANGE_DEBOUNCE_MS). If you're still scrolling, the timer restarts. We don't want to hit the server for every pixel of movement.
  3. When you pause, it checks: do we have rows 15–75? (That's the drawn range plus a 10-row prefetch margin, PREFETCH_THRESHOLD.) We only have 0–50, so no.
  4. It fetches rows 0–90 (25 spare rows on each side), then cancels the old subscription.
  5. While that loads, rows we don't have show as grey skeletons. When the new rows arrive, they replace the old slice.

What "generation" means Each fetch gets a ticket number (generationRef). If you scroll again before an older fetch finishes, messages from the older fetch carry an out-of-date ticket and are ignored. Its subscription is cancelled as soon as it starts. This prevents old rows from appearing in the wrong place.

"oof" (out of focus) is AMPS's way of saying "this row no longer matches your query", for example because it was deleted or no longer matches your filter. We remove that row.

10. The flush: applying changes in batches

If a price ticks 20 times a second, we don't want to redraw 20 times a second. The eye can't tell, and the CPU pays for it. So changes wait in a buffer, and a flush applies them all together.

When does a flush happen?

  • At most once every 250ms (FLUSH_INTERVAL_MS). That's 4 times a second, matching the server's own 250ms conflation (AMPS merging rapid changes to the same row).
  • Inside an animation frame (requestAnimationFrame). That's the moment the browser is about to repaint the screen. It also means that if the browser tab is hidden, flushes pause automatically and cost nothing.
sequenceDiagram
  participant M as Messages
  participant B as Buffer
  participant F as Flush
  participant R as React / screen

  M->>B: L42 changed (t = 0 ms)
  Note over B,F: first change, flush scheduled for t = 250 ms
  M->>B: L17 changed (t = 40 ms)
  M->>B: L42 changed again (t = 90 ms), merged
  M->>B: L08 changed (t = 200 ms)
  F->>B: t = 250 ms, next animation frame: take everything
  F->>F: apply 3 rows in ONE pass, skip any that did not really change
  F->>R: one state update, one redraw of 3 rows

What the flush does, step by step

  1. Takes everything from the buffer and empties it.
  2. If the total row count changed, updates it.
  3. For each changed row, looks up its position using a key index (a Map, so it's instant).
  4. Compares the new values with the old ones. If nothing actually changed, it skips that row, so the row keeps its identity and won't redraw.
  5. Copies the row list once, puts the updated rows in, and removes any "oof" rows.
  6. Hands the finished list to React in one go.
BeforeA timer every 500ms. For each change it searched the whole list and copied it, so 10 changes meant 10 full copies. Rows were redrawn even when the value was identical.
AfterA timer plus animation frame every 250ms. One copy per batch, unchanged rows skipped, paused when the tab is hidden, and the row count is included in the same batch.

11. Rendering only what changed (memoization)

Memoization means a component remembers what it drew last time and skips redrawing if its inputs are the same.

Each row is a DataTableRow component that only redraws when one of these changes:

  • its data object (the flush creates a new object only for rows that really changed),
  • whether it's selected (checkbox),
  • which columns are shown,
  • the row height.

The header (DataTableHeader) only redraws when sorting, filters or the select-all checkbox change. It doesn't redraw on price ticks.

Measured in a test with fake data With 3 of 30 visible rows ticking 4 times a second, about 60 cell renders happened in 2 seconds, compared with about 480 without memoization. Scrolling for 3 seconds produced no long tasks: the median frame took 8.3ms (the headless test browser ran at 120Hz). If you put a console.log inside DataTable, it will still print on every flush. That's expected: the function runs, but the rows underneath skip their work.

We only have ~70 of possibly thousands of rows, so sorting or filtering in the browser would give wrong answers. Instead, the server sorts and filters:

13. Connecting and disconnecting

In development, React deliberately mounts every component, unmounts it, and mounts it again (StrictMode). This helps catch bugs. Before, that meant a WebSocket was opened, then closed while still connecting, which triggered the browser warning.

Now the hook waits one "microtask" (a tiny moment) before connecting. React's mount–unmount–mount happens before that moment, so only the final mount ever connects.

15. Known limits and next steps

The subscription may still receive updates for the whole topic skip_n/top_n limit the first snapshot. We're assuming AMPS may still send live updates for every row in the topic. We drop the ones we don't need immediately, but the AMPS library still has to read (parse) each message first. If CPU stays high while idle, this is the most likely cause.

Proposed fix: after loading a page, subscribe only to those rows' keys (/listID IN (...)). This needs confirmation that listID is unique per row.
New rows don't appear on their own If a brand-new order would sort into the rows you're looking at, it shows up on the next fetch (scroll, sort or filter), not instantly. The earlier version had the same limitation.
"Select all" means "select all loaded rows" Only rows currently in the browser can be selected at once.
How to measure CPU fairly Run npm run build then npm run preview (it opens on port 4173). Close DevTools and check the tab in Chrome's Task Manager (Shift+Esc). The development server is several times slower and renders everything twice.
Dark mode The shadcn dark colours in index.css only apply when the dark class is on the page, and nothing currently adds it. Leftover Vite starter styles in index.css also change some colours when your OS is in dark mode, which looks half-finished. We still need to decide how dark mode should switch: follow the OS setting, or use a toggle button.
